# Class & Struct

## Identity

- Struct (값 타입)
    - 완전히 똑같은 복사본을 만든다면 두 Struct간의 **식별 연산자 `===(Identity Operator)`** 자체를 사용할 수 없다.
    - 즉 이 두개의 Struct는 **Stack**의 다른 위치에 존재하는 주소가 다른 완전한 별개 이다.
    - 오직 내부의 값이 같은지만 확인하는 `==`만 사용가능 하다.
    - 각각의 Struct 내부의 값을 변경할 수 있다.
    
- Class (참조 타입)
    - **Heap**에 있는 단 하나의 진짜 데이터를 여러 포인터에서 가리킨다.
    - 즉 같은 주소인지 확인하는 **식별 연산자 `===(Identity Operator)`**를 사용할 수 있다.
    - 하나의 포인터에서 Class 내부의 값을 변경한다면 다른 포인터에서도 변경된 값을 바라본다.
    
```swift
struct PersonStruct {
    var name: String
}

// Code 영역을 이용해 Stack에 첫 번째 실체 생성한다.
// p1이 원본
var p1 = PersonStruct(name: "철수")

// p1을 p2에 넣을때 스택에 p1과 완전히 똑같이 생긴 복사본이 생성된다.
var p2 = p1

// 복사본의 값을 변경
p2.name = "영희"

print(p1.name) // 출력: 철수 (원본 데이터는 변경 되지 않는다.)
print(p2.name) // 출력: 영희 (결국 복사본의 데이터만 변경이 된다.)
```

## Mutability


2. 불변성(Mutability)의 진실 : mutating 키워드
SwiftUI나 일반 코드를 짤 때, 구조체 안의 값을 바꾸는 함수에는 반드시 mutating을 붙여야 했죠? 클래스는 안 붙여도 되는데 말입니다. 그 이유가 바로 메모리 실체에 있습니다.

Struct: 스택에 저장됩니다. 만약 let p = Person()으로 선언하면, 스택의 공간 전체가 시멘트처럼 굳어버립니다. 그래서 내부 변수를 바꾸려 하면 컴파일러가 "야! 스택 굳었는데 어떻게 바꿔!" 하고 에러를 냅니다. 이걸 강제로 부수고 다시 쓰게 해주는 마법의 키워드가 mutating입니다.

Class: let c = Car()로 선언해도, 시멘트처럼 굳는 건 스택에 있는 '주소표(포인터)'뿐입니다. 창고(Heap)에 있는 진짜 자동차는 굳지 않았습니다! 그래서 주소만 안 바꾸면 창고 안의 차 색깔은 내 마음대로 바꿀 수 있습니다. (mutating이 필요 없는 이유)

3. 속도의 비밀 : 메서드 디스패치 (Method Dispatch)
이건 나중에 [Chapter 7. 시스템 밑바닥]에서 깊게 배울 내용의 예고편입니다.

Class: '상속'이 가능합니다. 부모 클래스의 함수를 자식이 덮어쓸(Override) 수 있죠. 그래서 앱이 실행될 때, "지금 부모 함수를 실행해야 돼, 자식 함수를 실행해야 돼?" 하고 매번 런타임에 vTable이라는 명부를 뒤져봐야 합니다 (Dynamic Dispatch). 이게 은근히 속도를 갉아먹습니다.

Struct: '상속'이 불가능합니다. 오직 하나뿐이죠. 그래서 컴파일러가 앱을 빌드할 때 "이 함수는 무조건 이 주소에 있어!" 하고 기계어에 하드코딩해 버립니다 (Static Dispatch). 찾는 과정이 없으니 속도가 미친 듯이 빠릅니다.
